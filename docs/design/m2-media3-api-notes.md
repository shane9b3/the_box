# Media3 1.11.1 API fact sheet (M2 playback core)

Verified against the real `-sources.jar` files for **androidx.media3 1.11.1** (`MediaLibraryInfo.VERSION = "1.11.1"`, media3-common `MediaLibraryInfo.java:32`). Nothing here is from memory.

## How to read this sheet

- Citation format: `module:path/File.java:line` where the path is relative to `androidx/media3/`. Lines are from the 1.11.1 sources.
- Sources were unzipped from `~/.gradle/caches/modules-2/files-2.1/androidx.media3/<module>/1.11.1/` (common, container, database, datasource, datasource-okhttp, decoder, exoplayer, exoplayer-hls, extractor, session). The modules that were not in the cache (`media3-ui`, `media3-ui-compose`, `media3-test-utils`, `media3-test-utils-robolectric`, `media3-exoplayer-dash`) were downloaded from `https://dl.google.com/dl/android/maven2/androidx/media3/<module>/1.11.1/`.
- FFmpeg extension sources: the repo carries `tools/ffmpeg/work/media/libraries/decoder_ffmpeg/...` (the media3 1.11.1 tag) and the built AAR `ffmpeg/libs/media3-decoder-ffmpeg-1.11.1-armeabi-v7a_arm64-v8a.aar` (public API verified with `javap`).
- Most of the player-side API is `@UnstableApi` (Kotlin needs `@OptIn(UnstableApi::class)`). `@ExperimentalApi` methods are flagged where seen.
- Constants that resolve to Android SDK values (for example `C.ENCODING_AC3 = AudioFormat.ENCODING_AC3`) are listed with the SDK int, marked "SDK".

Then **`builder.addHeader(RANGE, ...)`** (:405), `addHeader(USER_AGENT, ...)` (:408), `addHeader(ACCEPT_ENCODING, "identity")` (:411) when `FLAG_ALLOW_GZIP` is unset. - **Range logic:** the Range header is derived from `DataSpec.position`/`length` by `HttpUtil.buildRangeRequestHeader(long position, long length)` (media3-datasource:datasource/HttpUtil.java:57): returns `null` only when `position == 0 && length == C.LENGTH_UNSET`; otherwise `"bytes=" + position + "-" + (length != LENGTH_UNSET ? position+length-1 : "")`. So: position > 0 always sends `Range`; length != LENGTH_UNSET always sends `Range`, even with position 0 (`bytes=0-N`).

If the body ends before that, `HttpDataSourceException(..., ERROR_CODE_IO_READ_POSITION_OUT_OF_RANGE, TYPE_OPEN)` (:~489).
- Non-2xx (OkHttpDataSource.java:~281-312): `if (!response.isSuccessful())`. Special case 416: if `Content-Range` document size equals `dataSpec.position` the open succeeds with length 0 (:285-292). Otherwise it reads the error body (`ByteStreams.toByteArray`), snapshots `response.headers().toMultimap()`, closes, and throws `new InvalidResponseCodeException(responseCode, response.message(), cause, headers, dataSpec, errorResponseBody)` where `cause` is a `DataSourceException(ERROR_CODE_IO_READ_POSITION_OUT_OF_RANGE)` for 416 and `null` otherwise.

- `HttpDataSourceException.createForIOException(IOException cause, DataSpec dataSpec, @Type int type)` — HttpDataSource.java:220 — error-code mapping: `SocketTimeoutException` -> `ERROR_CODE_IO_NETWORK_CONNECTION_TIMEOUT` (2002); `InterruptedIOException` -> `ERROR_CODE_FAILED_RUNTIME_CHECK` (1004, "should not cause the player to fail"); message matching `cleartext.*not permitted.*` -> `ERROR_CODE_IO_CLEARTEXT_NOT_PERMITTED` (2007, returned as `CleartextNotPermittedException`); anything else -> `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED` (2001). - Constructor rule (HttpDataSource.java:370): `assignErrorCode` converts `ERROR_CODE_IO_UNSPECIFIED` with `TYPE_OPEN` to `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED`.
- `InvalidContentTypeException(String contentType, DataSpec dataSpec)` — HttpDataSource.java:398 — code `ERROR_CODE_IO_INVALID_HTTP_CONTENT_TYPE` (2003).
- Malformed URL: `HttpDataSourceException("Malformed URL", dataSpec, ERROR_CODE_FAILED_RUNTIME_CHECK, TYPE_OPEN)` (OkHttpDataSource.java:~379).
- `HttpDataSourceException` extends `DataSourceException` (public final `reason`), so the player reports `reason` as `PlaybackException.errorCode` (ExoPlayerImplInternal.java:~993 `catch (DataSourceException e) { handleIoException(e, e.reason); }`).

`configureRetry` (:1094-1124) decides the retry position:

```java
if (isLengthKnown || (seekMap != null && seekMap.getDurationUs() != C.TIME_UNSET)) {
  // We're playing an on-demand stream. Resume the current loadable, which will
  // request data starting from the point it left off.
  extractedSamplesCountAtStartOfLoad = currentExtractedSampleCount;
  return true;
} else if (prepared && !suppressRead()) {
  // We're playing a stream of unknown length and duration. Assume it's live, ... there's no way
  // to continue loading from where a previous load finished, so it's necessary to load from the
  // start whenever commencing a new load. Deferring the retry until we run out of buffered data ...
  pendingDeferredRetry = true;
  return false;
} else {
  // ... no value in deferring the retry because there's no buffered data to be read. This case
  // also covers an on-demand stream with unknown length that has yet to be prepared.
  notifyDiscontinuity = prepared;
  lastSeekPositionUs = 0;
  extractedSamplesCountAtStartOfLoad = 0;
  for (SampleQueue sampleQueue : sampleQueues) { sampleQueue.reset(); }
  loadable.setLoadPosition(0, 0);
  return true;
}
```

Reading of this:

- **Length known** (`isLengthKnown`: `open()` returned a value other than `C.LENGTH_UNSET`, set at :932 via `onLengthKnown()`, e.g. the server sent `Content-Length`) **or duration known**: retry reuses the same loadable and re-opens at `positionHolder.position` = the extractor's current input position (non-zero), which `OkHttpDataSource` turns into `Range: bytes=N-`. This is the case for a "live" TS URL that answers with a Content-Length.
- **Length and duration unknown, prepared, and samples still being consumed** (`!suppressRead()`): no immediate retry (`return false` -> `Loader.DONT_RETRY`, `pendingDeferredRetry = true`). When the sample queues drain, `maybeStartDeferredRetry` (:729-743) sets `pendingResetPositionUs = 0`, resets queues, `notifyDiscontinuity = true`, and calls `onContinueLoadingRequested`; `startLoading()` (:1058) creates a **new** `ExtractingLoadable` (position 0 in its ctor) and, because prepared, calls `loadable.setLoadPosition(seekMap.getSeekPoints(0).first.position, 0)` (:1071); for `Unseekable` that position is 0. **No Range header.** `continueLoading` returns false while `pendingDeferredRetry` (:511).
- **Length and duration unknown, and not prepared (or reads already suppressed)**: `loadable.setLoadPosition(0, 0)` and an immediate retry from 0. **No Range header.**
- `isLive` / data type: `setSeekMap` (:968-971): `isLive = !isLengthKnown && seekMap.getDurationUs() == C.TIME_UNSET; dataType = isLive ? C.DATA_TYPE_MEDIA_PROGRESSIVE_LIVE : C.DATA_TYPE_MEDIA;` `getMinimumLoadableRetryCount(dataType)` is read at `startLoading` (:1081) and at `maybeThrowError` (:662). Errors that reach `onLoadError` before the seek map is set use `C.DATA_TYPE_MEDIA` in the `MediaLoadData` (:855) but the retry count comes from `dataType` (field default `DATA_TYPE_MEDIA`, so 3 until `setSeekMap`, then 6 for live).
- Seeks into unseekable media are treated as seeks to 0 (`positionUs = seekMap.isSeekable() ? positionUs : 0;` :590; `getAdjustedSeekPositionUs` returns 0 :632), and for `DATA_TYPE_MEDIA_PROGRESSIVE_LIVE` it never seeks inside the buffer (:603), always reloading from the loadable position.
- Hazard worth designing around: the `finally` block stores `getCurrentInputPosition()` into `positionHolder.position` before `configureRetry` runs, so in the first branch (length known) the retry is non-zero by design. A `FakeDataSource` with `setSimulateUnknownLength(true)` still honours non-zero `position` (FakeDataSource.java:105-160), so it does not model a real unseekable live server.

## 20. Other 1.11.x notes found in source

- No release-notes text ships inside the sources jars. What I could confirm from the code (not from a changelog):
  - `ExoPlayer.Builder.experimentalSetDynamicSchedulingEnabled` defaults to `true` and is `@ExperimentalApi` with a removal TODO (ExoPlayer.java:~567-577, 530).
  - `MediaCodecVideoRenderer` frame-rate strategy default is `ONLY_IF_SEAMLESS` at both `ExoPlayer.Builder` and renderer level; `Surface.setFrameRate` is called only on API 30+ (section 8).
  - Stuck-player detection with `StuckPlayerException` is on by default (section 6).
  - `DefaultLoadControl` gained local-playback vs streaming parameter sets (section 5).
  - The `LoadControl` methods take `PlayerId`/`Parameters`; `Renderer[]`-based overloads are dead.
  - `MediaCodecVideoRenderer` constructors are deprecated in favour of `Builder`; `MediaCodecInfo.isFormatSupported` takes a `Context`.
  - `DefaultAudioSink.Builder` offload/track-provider setters are deprecated in favour of `setAudioOutputProvider`; `AudioCapabilities.getCapabilities` 1-/3-arg forms are deprecated.
  - `PlaybackException` has `4006` and `5004`.
  - `ExoPlayer.Builder` has `setName`, `setAudioOutputProvider`, `setSuitableOutputChecker`, `setScrubbingModeParameters`.
  - `Player.PLAYBACK_SUPPRESSION_REASON_SCRUBBING = 4`.
- `DefaultHttpDataSource.Factory.setAllowCrossProtocolRedirects(boolean)` exists at DefaultHttpDataSource.java:153 (`@UnstableApi`), plus `setKeepPostFor302Redirects(boolean)` :216; defaults `DEFAULT_CONNECT_TIMEOUT_MILLIS = 8 * 1000` (:242), `DEFAULT_READ_TIMEOUT_MILLIS = 8 * 1000` (:245). For `OkHttpDataSource` the equivalents are OkHttpClient settings (`connectTimeout`, `readTimeout`, `followRedirects`, `followSslRedirects`).
- OkHttp: Media3's POM pins `okhttp:4.12.0`; the repo resolves `5.5.0` via `okhttp-android`. All 26 OkHttp members `OkHttpDataSource` calls exist in 5.5.0 (section dependency, above).
- `@UnstableApi` is pervasive: `OkHttpDataSource.Factory.setCacheControl/setTransferListener/setContentTypePredicate/setDefaultRequestProperties`, `DataSink`, `TeeDataSource`, `ResolvingDataSource`, `StatsDataSource`, `DataSourceException`, `LoadControl`, `DefaultLoadControl`, `LoadErrorHandlingPolicy`, `TsExtractor`, `DefaultTsPayloadReaderFactory`, `TimestampAdjuster`, `MediaCodecSelector`, `AudioSink`, `MediaSessionService`'s foreground APIs and most `MediaSession.Builder` setters.

## Not verified / not found

- **Runtime behaviour was not exercised.** Everything above is from reading source and signatures (plus `javap` of the FFmpeg AAR and static symbol comparison of `OkHttpDataSource` against OkHttp 5.5.0). Nothing was run on a device, emulator or Robolectric.
- **No 1.11.x release notes** (GitHub `RELEASENOTES.md`) were consulted, as instructed to use only the sources. Statements about what is "new in 1.11" are inferred from deprecation markers and API presence, not from a changelog.
