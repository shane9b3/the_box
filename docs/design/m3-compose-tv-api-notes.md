## 1. Custom drawing in Compose

### 1.1 Entry points

- **`Modifier.drawBehind(onDraw: DrawScope.() -> Unit)`** draws before the node's content, no cache; node re-draws when snapshot state read inside `onDraw` changes (draw phase only, no recomposition/layout). — `ui:1.12.1`, `commonMain/androidx/compose/ui/draw/DrawModifier.kt:93`; `DrawBackgroundModifier.draw()` = `onDraw(); drawContent()` (:118-121).
- **`Modifier.drawWithCache(onBuildDrawCache: CacheDrawScope.() -> DrawResult)`**: cache lambda re-runs when the size changes or any state read **in the cache lambda** changes; the returned `onDrawBehind { }` / `onDrawWithContent { }` runs every draw. — same file :145; `CacheDrawScope` :344, `onDrawBehind` :405, `onDrawWithContent` :411. Doc text (:128-139): "persisted across draw calls as long as the size of the drawing area is the same or any state objects that are read have not changed".
- **`CacheDrawScope` extras**: `size`, `layoutDirection`, density (it is a `Density`), `obtainGraphicsLayer(): GraphicsLayer` (managed, recycled on invalidation, released on detach) and `GraphicsLayer.record(density, layoutDirection, size, block)`. — :344-400. Use for a pre-rendered static layer (e.g. the time-ruler or static chrome) drawn with `drawLayer(layer)`.
- **`Canvas(modifier, onDraw)`** composable is just `Spacer(modifier.drawBehind(onDraw))`; "You MUST specify size". Lambda runs in the draw phase, no `@Composable` calls. — `foundation:1.12.1`, `commonMain/androidx/compose/foundation/Canvas.kt:42`.
- **How to use it here**: the guide grid is one node, `Modifier.fillMaxSize().focusRequester(..).onPreviewKeyEvent(..).focusable().drawWithCache { build per-size objects; onDrawBehind { GuideRenderer.draw(this, state) } }`. Read scroll/focus offsets as `State` **inside** `onDrawBehind` (invalidates draw only), never inside the cache lambda (which would rebuild the cache on every scroll tick).

### 1.2 DrawScope primitives (ui-graphics 1.12.1, `commonMain/androidx/compose/ui/graphics/…`)

- **Rounded rect**: `DrawScope.drawRoundRect(color: Color, topLeft: Offset = Zero, size: Size = this.size.offsetSize(topLeft), cornerRadius: CornerRadius = CornerRadius.Zero, style: DrawStyle = Fill, alpha: Float = 1f, colorFilter: ColorFilter? = null, blendMode: BlendMode = DefaultBlendMode)` — `drawscope/DrawScope.kt:622`. Brush overload :596 has `alpha` before `style`.
- **Fill + stroke**: draw two calls: `drawRoundRect(fill, topLeft, size, cr)` then `drawRoundRect(strokeColor, topLeft, size, cr, style = Stroke(width = px))`. `Stroke(width: Float = 0f (hairline), miter = 4f, cap = Butt, join = Miter?, pathEffect = null)` — `DrawScope.kt:960-976`. Width is in **px** inside the DrawScope; use `1.dp.toPx()` (== 1 design px under `BoxDesignScale`). A stroke is centred on the rect edge (Skia semantic, [unverified-platform]); to keep a border inside the cell, inset topLeft/size by `width/2` and the radius by `width/2`.
- **Clip**: `DrawScope.clipRect(left=0f, top=0f, right=size.width, bottom=size.height, clipOp: ClipOp = ClipOp.Intersect, block)` (`DrawScope.kt:202-209`, implemented as `withTransform({ clipRect(...) }, block)`). `ClipOp` is a value class with `Difference` and `Intersect` only (`graphics/ClipOp.kt:28-35`). `clipPath(path, clipOp)` exists on `DrawTransform` (`drawscope/DrawTransform.kt:124`).
- **Transform**: `DrawScope.translate(left, top, block)` :119; `inset(...)` :61-104; `DrawScope.withTransform(transformBlock: DrawTransform.() -> Unit, drawBlock: DrawScope.() -> Unit)` :245. `DrawTransform` has `inset`, `clipRect`, `clipPath`, `translate`, `rotate`, `scale` (`DrawTransform.kt:93-155`). All are `inline`, scoped save/restore; cheap.
- **Native canvas**: `inline fun DrawScope.drawIntoCanvas(block: (Canvas) -> Unit)` = `block(drawContext.canvas)` (`DrawScope.kt:233`); `val Canvas.nativeCanvas: android.graphics.Canvas` — `ui-graphics:1.12.1`, `androidMain/androidx/compose/ui/graphics/AndroidCanvas.android.kt:53`. Compose `Canvas` interface also offers `drawRoundRect(left, top, right, bottom, radiusX, radiusY, paint)`, `drawImageRect`, `drawPath`, `clipRect(rect, clipOp)` (`Canvas.kt:276-488`) for use with a reused `Paint`.
- **Bitmaps**: `DrawScope.drawImage(image: ImageBitmap, srcOffset, srcSize, dstOffset, dstSize, alpha, style, colorFilter, blendMode, filterQuality)` (`CanvasDrawScope.kt:203-270`; default `filterQuality = DefaultFilterQuality`). `android.graphics.Bitmap.asImageBitmap()` converts a Coil bitmap.
- **BlendMode** values: Clear, Src, Dst, SrcOver (the default, `DrawScope.DefaultBlendMode` :928), DstOver, SrcIn, DstIn, SrcOut, DstOut, SrcAtop, DstAtop, Xor, Plus, Modulate, Screen, Overlay, Darken, Lighten, ColorDodge, ColorBurn, Hardlight, Softlight, Difference, Exclusion, Multiply, Hue, Saturation, Color, Luminosity (`graphics/BlendMode.kt`, lines 53-417). **Caution**: `Clear`/`DstOut` etc. only do what you expect inside an offscreen layer; `CompositingStrategy` doc (`graphics/layer/CompositingStrategy.kt:44-50`) says masking with `BlendMode.Clear` needs `Offscreen`. In this app never draw such modes on any ancestor of the video hole (see §4.5).

### 1.3 Text drawing

- **`rememberTextMeasurer(cacheSize: Int = DefaultCacheSize (8)): TextMeasurer`** — `ui:1.12.1`, `commonMain/androidx/compose/ui/text/TextMeasurerHelper.kt:42`. Reads `LocalFontFamilyResolver`, `LocalDensity`, `LocalLayoutDirection`; remembered keyed on all four. `cacheSize = 0` disables the cache.
- **`TextMeasurer.measure(text: String, style: TextStyle = Default, overflow: TextOverflow = Clip, softWrap: Boolean = true, maxLines: Int = Int.MAX_VALUE, constraints: Constraints = Constraints(), layoutDirection, density, fontFamilyResolver, skipCache: Boolean = false): TextLayoutResult`; an `AnnotatedString` overload adds `placeholders`. — `ui-text:1.12.1`, `commonMain/androidx/compose/ui/text/TextMeasurer.kt` (String overload ~:190, AnnotatedString ~:134).
  - `constraints.maxWidth` = layout width; `maxHeight` limits line count when ellipsizing; `minWidth` sets the minimum reported size; `minHeight` is a no-op (KDoc :118-122).
  - `softWrap = false` + `overflow = Ellipsis` is special-cased to `maxLines = 1` with maxWidth honoured (code at ~:306-330). That is the right setting for one-line programme titles: `measure(title, style, overflow = TextOverflow.Ellipsis, softWrap = false, maxLines = 1, constraints = Constraints(maxWidth = cellWidthPx))`. With `softWrap = false` and `overflow = Clip` the width constraint is ignored (`widthMatters = softWrap || overflow.isEllipsis`).
- **Cache** (`TextMeasurer.kt:362-455`): LRU of `cacheSize` entries (default 8, "If text layout is always called with different inputs, this number is a good stopping point"). Key = text + layout-affecting style + placeholders + maxLines + softWrap + overflow + density + layoutDirection + fontFamilyResolver (identity) + **constraints**. Colour, brush, shadow, decoration are **not** in the key, so recolouring a cached layout is free. A hit returns `cacheResult.copy(layoutInput, size)` (a new small object). Stale async-font results are dropped (`hasStaleResolvedFonts`).
  - **Consequence**: a guide with ~100+ visible cells overflows an 8-entry LRU every frame. Either size it (`rememberTextMeasurer(cacheSize = 256)`) or, better, own the cache: key `TextLayoutResult` by `(programme stable id, widthPx bucket, styleKind)` in the renderer and reuse across frames. The built-in LRU lookup itself allocates a key object per call.
- **`DrawScope.drawText`** (`ui-text:1.12.1`, `commonMain/androidx/compose/ui/text/TextPainter.kt`):
  - `drawText(textMeasurer, text: String, topLeft, style, overflow, softWrap, maxLines, size: Size = Unspecified, blendMode)` :208 and an `AnnotatedString` overload :143. They call `measure` on **every draw**, then `withTransform({ translate; clip })` and `multiParagraph.paint`.
  - **Trap**: with `size = Size.Unspecified` the constraints become `maxWidth = ceil(this.size.width - topLeft.x)` (`textLayoutConstraints`, ~:395-420). The constraint then differs for every x, so the LRU never hits. **Always pass an explicit `size`** (width = cell width px, height = line box) to get stable constraints.
  - `drawText(textLayoutResult, color = Unspecified, topLeft, alpha = NaN, shadow, textDecoration, drawStyle, blendMode)` :257 and a `brush` overload :317 paint a pre-made layout; "cannot relayout when async font loading resolves". This is the allocation-free path for the hot loop: measure outside `onDrawBehind` (or in the renderer's cache), call this inside.
  - **Allocation**: yes. The measurer overloads allocate `AnnotatedString`, `TextLayoutInput`, a cache key, a copied `TextLayoutResult`, and two lambdas (`withTransform`) per call. The `TextLayoutResult` overload allocates only the `withTransform` lambdas (inline, so effectively none) plus `Color.modulate` math; it clips only if `hasVisualOverflow && overflow != Visible`.
  - Colour: `layoutInput.style.color` is used if `color` is Unspecified. `MultiParagraph.paint(canvas, color, shadow, decoration, drawStyle, blendMode)` mutates the paragraph's paint ("Any change caused by overriding parameters are permanent" — `Paragraph.kt` paint KDoc ~:303-310), so passing a different colour per call on a shared layout is fine but not thread-safe.
- **Lower level**: `Paragraph(text, style, constraints, density, fontFamilyResolver, spanStyles, placeholders, maxLines, overflow): Paragraph` (`Paragraph.kt:~449`) and `MultiParagraph(intrinsics, constraints, maxLines, overflow)` (`MultiParagraph.kt:58`). `Paragraph` exposes `width`, `height`, `getLineLeft/Right/Top/Bottom/Width`, `getLineEnd(line, visibleEnd)`, `isLineEllipsized`, `getOffsetForPosition`, `getBoundingBox`, `paint(canvas, color|brush, …)`. Use only when you need width measurement without a `TextLayoutResult`; for most things `TextMeasurer` does the same with caching. `ParagraphIntrinsics.maxIntrinsicWidth` gives the unconstrained text width for "does the title fit" checks.
- **Measuring without draw**: `measure(...).size` is `IntSize`; `multiParagraph.width/height` are floats.
- **Native text path** (`drawIntoCanvas { it.nativeCanvas.drawText(...) }` with `android.graphics.Paint` + `StaticLayout`) avoids Compose's layout cache and gives full control, but loses `TextStyle` features (OpenType `tnum`, bundled-font weight resolution via `FontFamily`); not recommended unless profiling shows `TextMeasurer` cost. The tokens in `DesignTokens.Type` (`fontFeatureSettings = "tnum"`) rely on Compose's text stack.

## 2. Focus and keys on TV

### 2.1 Compose key pipeline (ui 1.12.1)

- **Order**: `FocusOwnerImpl.dispatchKeyEvent` (`commonMain/androidx/compose/ui/focus/FocusOwnerImpl.kt:352-375`) finds the focused node's nearest `KeyInput` node and walks ancestors: pre-visit `onPreKeyEvent` **root → focused** (outermost first), then (optionally) the embedded Android view, then post-visit `onKeyEvent` **focused → root**. First `true` wins. So `onPreviewKeyEvent` sees keys before children; `onKeyEvent` after children.
- **Default focus movement happens in the root `onKeyEvent`**: `AndroidComposeView`'s owner key handler maps keys via `KeyEvent.toFocusDirection()` (`androidMain/…/focus/FocusInteropUtils.android.kt:59-81`): `DirectionLeft/Right` → Left/Right; `DirectionUp`+`PageUp` → Up; `DirectionDown`+`PageDown` → Down; `DirectionCenter`/`Enter`/`NumPadEnter` → Enter; `Back`/`Escape` → Exit; `Tab`, `NavigatePrevious/Next` → Previous/Next; handled only for `KeyDown`. (`AndroidComposeView.android.kt:3636-3660`.) **Therefore a node that returns `true` for a key from `onKeyEvent`/`onPreviewKeyEvent` stops Compose's built-in focus traversal for that key.**
- **Key repeat is just more `KeyDown`s**: `KeyEvent.type` maps `ACTION_DOWN→KeyDown`, `ACTION_UP→KeyUp`, anything else (incl. `ACTION_MULTIPLE`) → `Unknown`; there is no separate repeat type, use `event.nativeKeyEvent.repeatCount`. — `ui:1.12.1`, `androidMain/androidx/compose/ui/input/key/KeyEvent.android.kt` (`key = Key(nativeKeyEvent.keyCode)`, `type`, `utf16CodePoint`).
- **Signature**: `value class KeyEvent(val nativeKeyEvent: NativeKeyEvent)` where `NativeKeyEvent = android.view.KeyEvent` (`commonMain/…/input/key/KeyEvent.kt:31`). `Modifier.onKeyEvent(onKeyEvent: (KeyEvent) -> Boolean)` / `onPreviewKeyEvent(...)` — `KeyInputModifier.kt:32/46`.
- **An unmatched `KeyUp` is dropped**: `FocusOwnerImpl.validateKeyEvent` (:584-604) tracks `keysCurrentlyDown`; a `KeyUp` whose `KeyDown` Compose never saw is not delivered. Matters if focus arrives mid-press.
- **No focused node**: dispatch starts from `rootFocusNode.nearestAncestor(KeyInput)` (:364); a node with `onKeyEvent` but no focus never sees keys. The grid node must be focused (`FocusRequester.requestFocus()`).
- **Focus plumbing signatures** (ui 1.12.1): `Modifier.focusRequester(FocusRequester)` (`FocusRequesterModifier.kt:48`); `FocusRequester.requestFocus(focusDirection = Enter): Boolean` (`FocusRequester.kt:83`) — if the modifier is not attached yet it **prints a warning and returns false** (`findFocusTarget`, :255-275); call from `LaunchedEffect` after the node is composed, or after `withFrameNanos`. `captureFocus()/freeFocus()` :101/127 (while captured, other focus requests are denied). `Modifier.focusProperties { canFocus; up/down/left/right/next/previous/enter/exit }` (`FocusProperties.kt:279`). `Modifier.onFocusChanged((FocusState)->Unit)` (`FocusChangedModifier.kt:33`) and `onFocusEvent` (`FocusEventModifier.kt:33`). `Modifier.focusTarget()` (`FocusModifier.kt:34`) is the primitive; `Modifier.focusable(enabled = true, interactionSource = null)` (foundation, `Focusable.kt:61`) adds semantics/interaction; `Modifier.focusGroup()` :95; `Modifier.focusRestorer(fallback)` (`FocusRestorer.kt:109`).
- **Keys exist as `Key.*` constants** (`ui:1.12.1`, `androidMain/…/input/key/Key.android.kt`, each `Key(KeyEvent.KEYCODE_…)`): `DirectionUp` :133, `DirectionCenter` :161, `Enter` :371, `NumPadEnter` :788, `Back` :75, `Menu` :495, `Info` :897, `Guide` :939, `ChannelUp` :904, `ChannelDown` :911, `LastChannel` :1176, `MediaPlay` :800, `MediaPause` :803, `MediaPlayPause` :806, `MediaStop` :809, `MediaRecord` :812, `MediaNext` :815, `MediaPrevious` :818, `MediaRewind` :821, `MediaFastForward` :824, `MediaSkipForward` :855, `MediaSkipBackward` :858, `MediaTopMenu` :852, `ProgramRed/Green/Yellow/Blue` :1016/1023/1030/1037, `PageUp/PageDown` :504/507, `Zero..Nine` :203-230, `NumPad0..` :740, `Captions` :960, `Bookmark` :953, `Settings` :967, `Search` :501, `MoveHome` :423. Compose has **no** `Key` for `KEYCODE_TV_NUMBER_ENTRY`, `KEYCODE_DVR`, `KEYCODE_TV`; construct `Key(android.view.KeyEvent.KEYCODE_x)` (value class over the int keycode) or compare `event.nativeKeyEvent.keyCode`.
- **Keycodes (platform, android.jar API 37)**: `CHANNEL_UP=166`, `CHANNEL_DOWN=167`, `GUIDE=172`, `INFO=165`, `LAST_CHANNEL=229`, `MENU=82`, `PROG_RED/GREEN/YELLOW/BLUE=183/184/185/186`, `MEDIA_PLAY=126`, `MEDIA_PAUSE=127`, `MEDIA_PLAY_PAUSE=85`, `MEDIA_STOP=86`, `MEDIA_NEXT/PREVIOUS=87/88`, `MEDIA_REWIND=89`, `MEDIA_FAST_FORWARD=90`, `MEDIA_RECORD=130`, `MEDIA_SKIP_FORWARD/BACKWARD=272/273`, `MEDIA_STEP_FORWARD/BACKWARD=274/275`, `TV_NUMBER_ENTRY=234`, `DVR=173`, `0..9 = 7..16`, `NUMPAD_0=144`, `DPAD_CENTER=23`, `ENTER=66`, `NUMPAD_ENTER=160`, `PAGE_UP/DOWN=92/93`. `KeyEvent.FLAG_LONG_PRESS=128`, `FLAG_CANCELED_LONG_PRESS=256`, `FLAG_TRACKING=512`. `getRepeatCount()`, `isLongPress()`, `getEventTime()`, `getDownTime()` exist. — `~/Library/Android/sdk/platforms/android-37.0/android.jar` via `javap -constants`.

### 2.2 Long-press OK

- **What tv-material itself does** (verified code): `Modifier.handleDPadEnter` in `tv-material:1.1.0`, `androidx/tv/material3/SurfaceImpl.kt:125-187`: for `DPAD_CENTER`/`ENTER`/`NUMPAD_ENTER` (`AcceptableEnterClickKeys` :230) on `ACTION_DOWN`: `repeatCount == 0` → press interaction; `repeatCount == 1` → `onLongClick()` and mark `isLongClick`; on `ACTION_UP` → `onClick()` unless a long click already fired. It returns `StopPropagation` for these keys. So **long press = first auto-repeat (repeatCount==1)**, which fires after the system's key-repeat timeout, not a fixed 500 ms.
- **Platform timing** [unverified-platform]: the first repeat arrives after `ViewConfiguration.getKeyRepeatTimeout()` (API present, `android.view.ViewConfiguration#getKeyRepeatTimeout()` / `getKeyRepeatDelay()` / `getLongPressTimeout()`; default values are AOSP constants, observed roughly 400–500 ms; not readable from stubs). `FLAG_LONG_PRESS` is set by the native input dispatcher on the `repeatCount == 1` event. Compose test input uses `InitialRepeatDelay = 500L`, `SubsequentRepeatDelay = 50L` to model this (`ui-test:1.10.0`, `commonMain/…/test/InputDispatcher.kt:94-99`).
- **Caveats for TV remotes**: some Bluetooth/IR-to-BT remotes and Fire OS builds do not auto-repeat DPAD_CENTER at all, or repeat only some keys. Reliable pattern if you need an exact ≥ 500 ms: on `KeyDown && repeatCount == 0` record `downTime = eventTime` and start a timer (coroutine `delay(ViewConfiguration.get(ctx).longPressTimeout)` or fixed 500 ms) in the grid's scope; on `KeyUp` cancel it and treat as short press if it has not fired; also accept `repeatCount >= 1` as an early trigger if the timer has not fired yet. Always swallow the matching `KeyUp` after a long press so OK does not also tune.
- **Combine**: one handler for both: `if (e.type == KeyDown) { if (e.nativeKeyEvent.repeatCount == 0) startTimer() else if (repeatCount>=1 && !fired) fire() } else if (KeyUp) { ... }`.

### 2.3 "Keys the device has"

- `KeyCharacterMap.deviceHasKey(int keyCode): Boolean` and `deviceHasKeys(int[]): boolean[]` (static; `android.view.KeyCharacterMap`), `InputDevice.hasKeys(int...): boolean[]`, `InputDevice.getDeviceIds()`, `InputDevice.getDevice(id)`, `isVirtual()`, `getSources()`; all present in API 37 stubs (`javap`). **Caveat**: `deviceHasKey` answers from key-layout files of all attached devices; many remotes report keys they do not physically have, and some remotes (e.g. Fire TV, Chromecast with Google TV) lack colour keys. Treat as a hint for showing legend chips only, never as a gate on handling a key.

### 2.4 Single focusable node owning all grid keys (recommended)

- **Fact**: a single node with `focusRequester + onPreviewKeyEvent/onKeyEvent + focusable` receives every key while focused, and returning `true` suppresses Compose focus traversal (see §2.1). That is exactly the virtual-focus pattern: one `focusable()` host, grid cell focus kept in state (`row`, `col`, scroll offsets), drawn by the renderer. — `FocusOwnerImpl.kt:352-375`, `FocusInteropUtils.android.kt:59-81`.
- Use `onPreviewKeyEvent` on the host (not `onKeyEvent`) so a child that happens to be focused (e.g. a tv-material `Surface` in a side panel overlay) cannot steal keys, and handle only the keys it owns; return `false` for the rest so `Back`, volume and media keys keep their normal routing.
- Edge between the grid and the groups panel (left edge): return `false` for `DirectionLeft` when at column 0 *and* set `Modifier.focusProperties { left = groupsRequester }` on the host, or call `groupsRequester.requestFocus()` yourself. Use `focusProperties` `enter`/`exit` if you need to remember the last cell when focus returns (`FocusProperties.kt:279`).
- **Held-key scrolling**: each repeat is a `KeyDown` with `repeatCount > 0`; coalesce at the frame level (apply at most one step per vsync, or switch to continuous time-based scroll while a direction is held and `repeatCount > 0`) to avoid frame-queue buildup. The `PlaybackController.zap(delta, isRepeat)` API already takes `isRepeat` (`PlaybackApi.kt:32`).

### 2.5 tv-material focus visuals (what to expect if used)

- `Surface`/`Card`/`Button`/`ListItem` all sit on `SurfaceImpl`: when focused they animate **scale** (default `focusedScale = 1.1f` for Surface `SurfaceDefaults.kt:136`, Card `Card.kt:471`, Button `ButtonDefaults.kt:138`), raise `zIndex` (0.5f), draw a **border** (2 dp for Surface/Button/ListItem, 3 dp for Card, `SurfaceDefaults.kt:169`, `Card.kt:489`) and an optional **glow**; `SurfaceImpl.kt:98-121` applies `.graphicsLayer { alpha; shape; clip = true }` and a second `graphicsLayer { alpha }` on the content box. A clickable Surface stays focusable when `enabled = false` and gives `focusedDisabledScale`.
- Implication: **never place a tv-material Surface/Card/Button as an ancestor of the video hole** (clip + alpha graphicsLayer). Fine as siblings above the SurfaceView. For the guide, the scale-up and glow do not match the design doc's focus visuals, so draw focus yourself and use tv-material only for chrome (tabs, buttons) with `scale = ButtonDefaults.scale(focusedScale = 1f)` overrides.

### 4.4 `graphicsLayer` pitfalls

- `Modifier.graphicsLayer {}` default `CompositingStrategy.Auto`: an `alpha < 1`, or a `RenderEffect`, forces an **offscreen buffer** (`graphics/layer/CompositingStrategy.kt:31-41`). `ModulateAlpha` avoids the buffer (:54-60) but changes overlap results.
- `clip = true` / `shape` clip and `alpha` on any **ancestor** of the SurfaceView breaks hole punching (see §4.5). tv-material's `Surface` applies exactly that on every focus-capable component (§2.5).
- Descendants of those layers are fine. Also fine: layers on siblings drawn above the surface.

### 4.5 SurfaceView z-order and the hole

- `PlayerSurface` (`media3-ui-compose:1.11.1`) is `AndroidView(modifier = modifier, factory = { createView(it) }, onReset = {}, update = { view = it })` creating `object : SurfaceView(context)` that only overrides `dispatchDraw` for the API-34 `SurfaceSyncGroup` workaround (only `SDK_INT == 34`). It applies **no** modifiers other than the caller's, calls **no** `setZOrderMediaOverlay`/`setZOrderOnTop`, and attaches with `LaunchedEffect`/`DisposableEffect` using `Player.setVideoSurfaceView`. — `tools/ffmpeg/work/media/libraries/ui_compose/…/PlayerSurface.kt:55-150` (tag `1.11.1`); corroborated by `javap -c` of the aar (`PlayerSurfaceKt` calls `AndroidView_androidKt.AndroidView`; no `setZOrder*` call sites) and the repo's `docs/design/m2-media3-api-notes.md:426-432`.
- Repo wiring: `VideoLayer` (`ui/src/main/kotlin/app/thebox/ui/playback/VideoLayer.kt:18-38`) wraps `PlayerSurface` with `Modifier.layout { fixed size from RectPx; place at left/top }` — a plain layout modifier, no layer/clip. Debug harness puts it as the first child of a plain `BoxWithConstraints` (`PlaybackDebugActivity.kt:187-200`).
- Platform behaviour [unverified-platform, AOSP `SurfaceView`]: a default SurfaceView sits **behind** the window and punches a transparent hole in the window's drawing at its bounds; Compose content drawn after it in the same window appears on top of the video. This works only if nothing between the SurfaceView and the window root renders into an offscreen layer or clips it away (alpha < 1, `RenderEffect`, `CompositingStrategy.Offscreen`, `clip` with shape), and nothing opaque is drawn over the hole. `setZOrderOnTop(true)` would put video over all Compose content; `setZOrderMediaOverlay(true)` only orders against other SurfaceViews. Neither is used. Keep the guide's opaque backgrounds out of the hole rect (draw panel backgrounds with a hole or around it), or draw nothing at the mini-player rect.

## 6. Reminders and alarms on Android TV

- **API surface (android.jar 37 stubs)**: `AlarmManager.setExactAndAllowWhileIdle(int, long, PendingIntent)` and a listener variant; `canScheduleExactAlarms()`; `setAlarmClock(AlarmClockInfo, PendingIntent)`; permissions `SCHEDULE_EXACT_ALARM`, `USE_EXACT_ALARM`, `POST_NOTIFICATIONS` (API 33), `USE_FULL_SCREEN_INTENT`; `NotificationManager.areNotificationsEnabled()`, `createNotificationChannel(...)`, `IMPORTANCE_HIGH = 4`; `PackageManager.FEATURE_LEANBACK = "android.software.leanback"`, `FEATURE_LEANBACK_ONLY`. — `platforms/android-37.0/android-stubs-src.jar`.
- **Permission rules** (developer.android.com "Schedule alarms" and "Behavior changes: schedule exact alarms" pages, fetched 2026-10-14):
  - Targeting 12+ you must declare `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM`, otherwise `setExact*`/`setAlarmClock` throw `SecurityException`. `OnAlarmListener`-based alarms do not need the permission.
  - `USE_EXACT_ALARM`: "granted automatically", cannot be revoked, limited to **calendar or alarm-clock apps**, subject to a Google Play policy. The doc says apps that do not qualify cannot publish with it in the manifest.
  - `SCHEDULE_EXACT_ALARM`: user-granted via special app access; "no longer pre-granted to most newly installed apps targeting Android 13 and higher" (denied by default, documented on the Android 14 page). Existing app installs that had it keep it on upgrade to 14.
  - A TV IPTV player is not a calendar/alarm-clock app, so plan on `SCHEDULE_EXACT_ALARM` + `canScheduleExactAlarms()` + `Intent(ACTION_REQUEST_SCHEDULE_EXACT_ALARM)`, and **a fallback when it is denied** (inexact `setAndAllowWhileIdle`, which the doc describes as firing within an hour on 12+ in the worst case; reminders with 1-minute lead need exact). Whether TV/Fire OS system settings expose the special-access screen at all is **not verified**; many TV images lack the "Alarms & reminders" settings activity, so a denied permission may be permanently denied. Revocation kills the app process and cancels all exact alarms (doc); listen for `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` and reschedule from `reminder` table rows.
  - Doze: "Alarms don't fire when the device is in Doze mode … deferred" for plain alarms; `setExactAndAllowWhileIdle` is the sanctioned exception. The doc does not state the 9-minute throttle (do not rely on a number).
- **WorkManager**: `PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS = 900000` (15 min), `MIN_PERIODIC_FLEX_MILLIS = 300000` (`work-runtime-2.12.0.aar`, `javap -constants`). Not suitable for "remind me 1 minute before"; fine as a reconciliation sweep that re-arms alarms.
- **What displays on TV** [unverified-platform; the TV notification design pages were not found at the URLs tried]: Google's Android TV home shows notifications in a notifications panel/overlay (not a phone-style shade); behaviour of heads-up banners for `IMPORTANCE_HIGH` varies by device image; Fire OS (Amazon) generally does **not** surface third-party app notifications to the user at all. Do not rely on a system notification as the only reminder UI. `POST_NOTIFICATIONS` is already declared (`app/src/main/AndroidManifest.xml:10`); the repo's `WorkNotifications` creates a channel on API 26+ with `Notification.Builder(context, CHANNEL_ID)` and falls back to the legacy builder below 26 (`data/…/work/WorkNotifications.kt:15-40`), which is the same pattern a reminder channel should use. `NotificationChannel` is an API 26 platform feature; Fire OS 5 (API 22) / Fire OS 6 (API 25) lack it, minSdk 25 means the < 26 fallback path matters on older Fire TV sticks.
- **Reliable matrix**:
  - App in the foreground (guide or playback visible): an in-process timer (coroutine `delay` / a single `Handler.postDelayed` keyed to the next pending `reminder`, re-armed when the table changes) is exact enough and needs no permission; show the in-app toast/banner overlay. This is the only fully reliable path on TV.
  - App backgrounded but process alive: the in-process timer still fires unless the system freezes the process; the in-app overlay is invisible to the user, so a notification or a `startActivity` from a broadcast (restricted on 10+ without a full-screen-intent or "display over other apps") is needed.
  - App not running: only `AlarmManager` (exact permission + a broadcast receiver that posts the notification / launches the app, within background-start limits) works; behaviour on TV images is device-specific.
- Data: the reminder row is keyed `(playlist_id, stable_key, start_min)` with `lead_sec`, `state` (0 pending, 1 fired, 2 dismissed, 3 orphaned) — see §8.4; `ReminderRepository.due(nowMin)` returns pending rows to arm.
