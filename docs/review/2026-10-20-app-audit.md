# App audit — 2026-10-20

Initial review of the working tree, including uncommitted time-shift, guide, editor and artwork work. Three delegated reviewers covered security, performance and TV UX; the lead inspected integration/build/test paths and reconciled findings. Reviewers cross-checked parental/Search behavior and time-shift ownership with one another. Application code was not changed during that initial review. The subsequent authorized fix pass is recorded below.

The strongest optimization targets are time-shift teardown and settings list bookkeeping. The most concrete privacy defect is stale Search results after parental relock. Search also needs a navigation and readability pass. These findings do not establish that ordinary playback is currently slow.

P2 means a defect worth fixing in the next hardening pass. P3 denotes a lower-priority hardening or measurement gap. No critical remote compromise or parental playback bypass was demonstrated. Source-confirmed findings below still need the indicated device/regression verification.

## Findings

### 1. P2 — Search retains protected metadata after parental relock

**Evidence:** `ui/src/main/kotlin/app/thebox/ui/search/SearchViewModel.kt:105` subscribes only to reminders. Access is sampled when a changed query runs at line 123; an unchanged query returns at line 110. The activity owns the ViewModel (`app/src/main/kotlin/app/thebox/MainActivity.kt:49`). `data/src/main/kotlin/app/thebox/data/parental/ParentalSessionImpl.kt:111` relocks when the app stops.

**Trigger/impact:** Unlock parental controls, search for protected content, press Home and return without process death. The retained results can still show protected channel names, logos and programme titles even when locked content should be hidden. Results can also persist across Search visits. TuneGuard still protects playback; this is metadata disclosure, not a stream-access bypass.

**Recommendation:** Derive searches from query plus current parental access and relevant content/settings versions. Immediately clear results and cancel in-flight work when access becomes more restrictive, then requery. Verify both foreground relock and timeout relock, including a query still running at relock.

### 2. P2 — Rejected time-shift preparation retains a ring during HLS playback

**Evidence:** `player/src/main/kotlin/app/thebox/player/controller/PlaybackControllerImpl.kt:2271` removes `c.tsPrepare`, then returns for a non-bufferable format at lines 2274–2276 without awaiting/abandoning its result. `TimeshiftSessionFactoryImpl.kt:135` records a completed grant; idle/discard checks at line 234 refuse cleanup while any grant remains.

**Trigger/impact:** With time-shift enabled, tune an HLS stream. Preparation can allocate a ring despite the stream ultimately being rejected for buffering. Stop has neither the pending prepare nor the grant to release. The factory retains it until another prepare or process death. Approximate retained pool: 4 MiB, or 2 MiB on a low-RAM device, plus the index. The initial file extent is about 64 MiB; physical disk consumption can be smaller when sparse allocation is used, and a reused ring file may be larger. Process death releases RAM/handles; stale files are removed by the next startup sweep. This is retained ownership, not a fresh multi-megabyte leak on every HLS tune.

**Recommendation:** Give every preparation a cancellation-safe owner. When buffering is rejected or a cycle ends, release any already-produced grant and dispose of a late completion. Cancellation alone does not dispose of an already-completed result. Extend `anHlsTuneIsNotBuffered()` to assert factory idleness, stop/trim cleanup and both early/late prepare completion.

### 3. P2 — Buffered channel changes can perform disk I/O on main

**Evidence:** The main-confined controller closes time-shift through `PlaybackControllerImpl.kt:2363`. `TimeshiftSessionFactoryImpl.kt:221` calls `storage.flushCounter()` synchronously; `TimeshiftStorageImpl.kt:176` takes `counterLock`, and line 220 calls `File.writeText`. The background flusher also persists while holding this lock.

**Trigger/impact:** Zap after the ring has saved bytes. Teardown can write the daily counter before the next tune proceeds, or block on the counter lock during another write. This is a definite blocking path; flash latency and visible frame/zap impact have not been measured on a TV.

**Recommendation:** Keep immediate in-memory accounting, but serialize counter persistence on a background writer. Preserve ordering so a delayed snapshot cannot replace newer accounting. Measure channel-change latency and main-thread disk operations with time-shift on/off and during background writes.

### 4. P2 — Regex safety validation permits expensive backtracking

**Evidence:** `core/src/main/kotlin/app/thebox/core/text/RegexSafety.kt:47` resets overlap tracking at parentheses. Consequently `^(a+)(a+)(a+)(a+)$` is accepted by `isRisky`. `ChannelNamePrefixImpl.kt:42` matches up to 256 characters synchronously without a deadline. `data/src/main/kotlin/app/thebox/data/rules/RuleMatcher.kt:52` cannot interrupt Android ICU mid-match; its elapsed-time check occurs after matching.

**Trigger/impact:** A user-configured rule or imported backup supplies the pattern, and a provider supplies a channel name of 255 `a` characters followed by `!`. A probe against the compiled validator returned `risky=false`. JDK 21 matching took approximately 32 ms for 64 `a`s, 139 ms for 128 and 2,006 ms for 255, each followed by `!`. The largest input fits the prefix cap. Import/rule processing can spend substantial CPU time per affected channel and delay other work behind the import mutex/transaction. Android timing is unmeasured; this is not an unauthenticated arbitrary-regex injection claim.

**Recommendation:** Prefer a linear-time matcher or a genuinely parsed, restricted regex language. Group boundaries must not erase overlap information. Add grouped-adjacent-quantifier cases and Android timing coverage. A coroutine timeout around an uninterruptible matcher is insufficient.

### 5. P2 — Back handling does not contain Search's context menu

**Evidence:** `ui/src/main/kotlin/app/thebox/ui/search/SearchScreen.kt:89` handles Back on the results `Column`, while the context menu is its sibling at line 138. The menu requests actual focus at line 322. `ui/src/main/kotlin/app/thebox/ui/input/KeyRouterImpl.kt:168` passes Search keys through when its field is not idle, including when a menu is open. The focused menu subtree has no Back handler.

**Trigger/impact:** Search, hold OK on a result, then press Back. The handler intended to dismiss the menu is outside the focused event ancestry, so Back can fall to Activity behavior and leave the app. The menu also lacks explicit focus containment. The source path is confirmed; exact behavior across device Back implementations was not executed.

**Recommendation:** Put dismissal handling on a shared ancestor, constrain focus to the modal, and restore the source result after dismissal. Verify Back, edge D-pad movement, all menu actions and return focus on a real remote.

### 6. P2 — Search long-OK depends on remote-generated repeats

**Evidence:** `SearchScreen.kt:239` detects long press through native `repeatCount`/`isLongPress`. Search bypasses the shared router's timer-based long-press path.

**Trigger/impact:** A remote sends one Down and a later Up without repeat events. Holding OK selects the result on release instead of opening its context menu. Hardware variation makes favorites/reminder actions inconsistent.

**Recommendation:** Reuse timed long-press handling, cancel on focus loss/canceled events, and suppress the short action after a long action. Verify both repeating and non-repeating remotes; preserve five-way D-pad reachability.

### 7. P2 design — Search text is unusually small for TV

**Evidence:** `SearchScreen.kt:275`–293 uses 15 design px for metadata, 17 for secondary text and 19 for titles. `ui/src/main/kotlin/app/thebox/ui/theme/BoxDesignScale.kt:59` makes one design text unit one pixel at 1920×1080. On the documented xhdpi TV UI, these are approximately 7.5, 8.5 and 9.5 system sp. These values are smaller than the updated guide's typography.

**Impact/recommendation:** The dense cards can be legible at a desk but difficult from normal TV viewing distance. Start with titles around 30–36 design px (15–18 equivalent system sp) and metadata around 24–28 design px (12–14 equivalent sp), enlarge cards/rows to fit, and verify actual text at 720p, 1080p and 4K UI resolutions. Those are proposed starting tokens, not a claimed Android/Play minimum. Use a shared semantic type scale instead of isolated overrides. [Android TV typography guidance](https://developer.android.com/design/ui/tv/guides/styles/typography) prioritizes legibility at a glance.

### 8. P2 — Paged settings lists eagerly build keys for every row

**Evidence:** `ui/src/main/kotlin/app/thebox/ui/settings/SettingsScreen.kt:308` creates `Array(count)` and strings for both loaded and unloaded rows whenever the page model changes. The LazyColumn starts at line 326, after this full-count work.

**Trigger/impact:** Open a channel-backed settings list with a large playlist and load more pages. A 20,000-row list builds approximately 20,000 keys even when only a small slice is loaded. Every replaced page model can repeat the scan/allocation on the composition thread. This is an O(total rows) path despite paged data and lazy row rendering; its frame cost is unmeasured.

**Recommendation:** Derive keys on demand, with stable namespace-safe placeholder keys. Validate duplicate identities over loaded data rather than allocating for the total count. Benchmark opening/paging large channel lists; the existing settings journey's Playlists page does not cover this case.

### 9. P2 — Per-tune grant metadata grows until the ring is rebuilt

**Evidence:** `player/src/main/kotlin/app/thebox/player/timeshift/TimeshiftSessionFactoryImpl.kt:136` inserts grants into `lengths` and `limits`. `start()` reads them at lines 192–193 and removes only the `granted` entry at line 208. `abandon()` also leaves metadata behind. The two maps clear only in `closeRingLocked()` at lines 262–263, while equal-size zaps reuse the existing ring.

**Impact/recommendation:** Long-running buffered zapping accumulates small grant/map/boxed-value objects in O(zaps) memory. This is separate from finding 2 and does not multiply the ring allocation per zap. Consume metadata with `remove()` on start and remove abandoned/superseded entries. Add repeated prepare/start/close and prepare/abandon tests asserting bounded bookkeeping.

### 10. P2 accessibility — Guide caches TalkBack state and exposes no activation action

**Evidence:** `ui/src/main/kotlin/app/thebox/ui/guide/grid/GuideGridHost.kt:86` caches `touchExplorationOn(context)` with `remember`, without observing later changes. The semantics at line 108 advertise a button but do not provide `onClick` or custom accessibility actions.

**Trigger/impact:** Enable TalkBack through the accessibility shortcut while the guide remains composed. Programme descriptions remain disabled until composition is recreated. A role label alone also does not provide semantic activation/browsing.

**Recommendation:** Observe accessibility/touch-exploration changes and provide meaningful activate/browse actions or virtual programme semantics. Keep the single custom draw node; an accessibility layer does not require replacing it with thousands of composed cells. Verify on a TV with TalkBack enabled before and after launch.

### 11. P2 release hardening — Release signing silently falls back to debug

**Evidence:** `app/build.gradle.kts:50` selects the debug signer when release signing properties are absent. This is documented scaffold behavior; no evidence shows an APK built this way was distributed.

**Impact/recommendation:** A release artifact can be produced with an unintended signing identity, affecting trusted distribution and later updates. Fail release packaging without valid production signing; keep the explicit benchmark/debug signer. Verify the release certificate in the distribution pipeline.

### 12. P3 hardening — LAN rejection handling bypasses the worker cap

**Evidence:** `core/src/main/kotlin/app/thebox/core/setup/lan/LanHttpServerImpl.kt:111` starts a new unmanaged `box-lan-busy` thread for every over-limit connection. These connections bypass the normal active set, watchdog and stop cleanup.

**Impact/recommendation:** A connection flood while phone setup is open can create unbounded thread churn. Close excess connections directly or use bounded rejection handling. The small 503 usually fits TCP buffers promptly; sustained blocked-thread exhaustion was not demonstrated, so this is a hardening finding rather than a proven severe DoS exploit.

## Android TV design alignment

The single-player/surface architecture, custom guide renderer, prominent focus indication, remote key tables, system caption integration and avoidance of live blur are good foundations. Maintain those while addressing the specific paths above.

- **Navigation:** All primary actions need a clear D-pad path, visible focus, predictable Back dismissal and restored list position. Menu/color/media keys can be shortcuts; they should not be the only route. Apply this especially to Search, which has its own focus and key handling. [TV quality requirements](https://developer.android.com/docs/quality-guidelines/tv-app-quality).
- **Text scaling:** `BoxDesignScale.kt:59` deliberately pins `fontScale=1`, following the approved fixed-canvas baseline. This is design debt, not an accidental departure from that baseline. Current [Android TV accessibility guidance](https://developer.android.com/training/tv/accessibility#text-scaling) asks apps to respect user text scaling and rearrange content. Start with flexible Search/settings layouts and an optional larger guide density with fewer rows. Changing the density value alone would risk clipping existing fixed layouts.
- **Safe area:** Google's layout guidance uses a 960×540 mdpi reference with roughly 5% safe margins for important content: approximately 48dp horizontal and 27dp vertical, or 96×54 in this app's 1920×1080 design units. Background/video can extend to the edge. Search currently uses 64 design px at the sides and 40 at the bottom (`SearchScreen.kt:88`), so audit critical text/controls under simulated overscan and consider a configurable safe area. This is a device-compatibility recommendation; clipping was not demonstrated. [Layouts for TV](https://developer.android.com/design/ui/tv/guides/styles/layouts).
- **Exit:** The default double-Back exit and optional confirmation are approved product decisions (`core/.../settings/SettingsStore.kt:98`). Google recommends a simple Back path to the launcher without exit gating. Consider ordinary Back as the default, retaining any deliberate preference only after product review. [Navigation on TV](https://developer.android.com/design/ui/tv/guides/foundations/navigation-on-tv).

## Performance opportunities and measurement gaps

1. **Generate the app-specific baseline/startup profiles.** The generator exists, but no profile files were found under `app/src`; automatic generation is disabled (`app/build.gradle.kts:97`). This does not mean dependency profiles are absent. Generate profiles for startup, guide scroll, Search/settings and channel changes, and verify the packaged artifact. Measure the result rather than promising a percentage gain. [Baseline Profiles documentation](https://developer.android.com/topic/performance/baselineprofiles/overview).
2. **Measure usable startup and first video separately.** `benchmark/.../StartupBenchmark.kt:21` uses StartupTimingMetric, but the app has no `reportFullyDrawn`/`ReportDrawn` call. `ui/.../root/AppRoot.kt:200` and line 344 allow a blank boot surface beyond the initial frame, with an eight-second safety cap. That cap is not a measured normal startup time. Signal when the selected destination is usable, and trace first media separately. [Android startup timing guidance](https://developer.android.com/topic/performance/issues/launch-time).
3. **Measure refresh query amplification.** Each merge transaction can invalidate channel observers; `data/.../guide/GuideLibraryImpl.kt:66` and line 109 rebuild lineups/counts before downstream distinct filtering. Count queries and capture frames during a large refresh before adding coalescing. Preserve prompt editor updates and final refresh delivery. This is a hypothesis about cost, not a measured bottleneck.
4. **Run the existing low-end TV gates.** Use release-like builds, time-shift on/off, large playlists, refresh during playback, fast zapping, standby/resume, limited free space and a long soak. Record frame overruns, zap P50/P90/P99, main-thread I/O, memory/FD/thread stability and ring cleanup. JVM timings and emulator CPU frame metrics cannot establish TV flash/GPU/thermal behavior.

## Feature and release assessment

The implemented live-guide, mini/full player, catch-up, local TS time-shift, channel editor, setup/settings, parental controls and backup paths form a coherent live-TV product. The findings concern consistency and hardening of those features, rather than a need to add broad new scope.

Recording/DVR, VOD/series and HLS time-shift omissions are documented scope decisions. The release updater is intentionally disabled pending repository/public keys (`app/src/main/kotlin/app/thebox/update/UpdateEndpoints.kt:18`); it should not be described as an active release capability. Existing AEAD credential storage, encrypted backup logins, disabled Android backup, fail-closed parental initialization, LAN pairing/origin checks and updater signature/hash/certificate checks are useful protections. Other backup records remain plaintext; the entire backup is not encrypted.

CI currently runs core/data/player/UI unit tests and assembles the app but omits `:app:testDebugUnitTest` (`.github/workflows/android.yml:40`), leaving integration adapters such as archive playback and settings reapply outside that test gate. Add the app tests and their report directory.

## Authorized fix pass

The owner requested implementation, delegation, review of the combined changes and emulator testing. The same three reviewers implemented separate areas and reviewed one another's designs; the lead implemented settings-key, accessibility, startup-reporting and release/CI changes. All pre-existing working-tree changes were preserved; nothing was committed.

| Finding | Implementation |
| --- | --- |
| 1 — protected Search results | Invalidate and clear on access/content changes; epoch-guard late responses; require exact current snapshots for actions, including async mutation checks. Subscribe to content only during Search visits and refresh retained queries on reentry. |
| 2 — rejected preparation | Explicit take/release ownership; IO disposal for HLS, stopped/canceled cycles and late completions. Skip obsolete queued preparations. Preserve a discard request until late grants settle. |
| 3 — main-thread counter writes | Coalesced serialized background persistence; short in-memory snapshots, disk outside accounting lock, atomic file replacement and failed-write retry state. |
| 4 — regex work | RE2/J 1.8 through a single wrapper, bounded compilation and linear matching; no Java/ICU fallback. Unsupported saved prefixes fall back to Auto; unsupported hide rules are disabled as BAD_REGEX. |
| 5–6 — Search menu/hold | Shared Back handling, directional focus containment/restoration and a cancelable 500 ms timer independent of native repeats. |
| 7 — Search readability | 30 design px titles, 24 design px metadata, larger cards/menu rows, and 96×56 design-pixel safe margins. |
| 8 — list keys | Derive keys on demand; validate duplicates across fixed/loaded rows only, in logical order. Regression covers a billion advertised rows with two loaded rows. |
| 9 — grant bookkeeping | Remove metadata on transfer, abandonment and supersession. Roll back partial start failures and clean up terminal failure followed by Stop. |
| 10 — guide accessibility | Observe accessibility/touch-exploration state; expose guarded activation/directional actions only for a nonempty active grid. Modal and inactive-grid states suppress stale descriptions. Preserve draw-only invalidation. |
| 11 — release signing | Remove production debug-signer fallback; require valid explicit signing before APK/AAB packaging. Partial properties do not break debug configuration. Existing profile plugin retains its debug fallback for unsigned parents. |
| 12 — LAN resources | Close overload sockets without creating threads or writing responses. Also close a connection rejected by the worker pool during shutdown. |
