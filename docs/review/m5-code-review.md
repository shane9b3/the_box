## Blockers (fixed)

### C-B1. The settings machine crashes when four pages are on the open path (first run: Matching report → Fix now → pick a channel)
- **Where:** `SettingsMachineImpl.kt:777-781` (`onPage`, page-cache eviction).
- **Problem:** `PAGE_CACHE = 3`. When a fourth page arrives and every cached page is the displayed one or on `path`, `pages.keys.first { it != displayed && it !in path }` throws `NoSuchElementException` (the `break` check comes after the `first`), inside `dispatch(SettingsEvent.Page)` on main: the app crashes. Mainstream paths with four pages on the path: first run Welcome → form → replace ImportProgress → replace GroupsReview → replace MatchingReport → **Fix now** → OK on a channel (`[FirstRun, MatchingReport, FixGuide(null), FixGuide(ch)]`); Settings → Playlists → Add playlist → Xtream → result card "Phone setup" (`SourceFormPages.kt:220/415`); Playlists → Playlist → Edit source → "Phone setup". It breaks §3.4.7's "Fix now". The back-ladder test stopped at depth 3, which is why nothing caught it. Reproduced: `java.util.NoSuchElementException: Collection contains no element matching the predicate.` at `SettingsMachineImpl.onPage`.
- **Fix (lead decision 2):** `val eldest = pages.keys.firstOrNull { it != displayed && it !in path } ?: break` (the path's pages are kept by design, §5 item 6). No contract change.
- **Tests:** `SettingsMachinePageCacheTest` (the three reviewer tests, adopted: `fourPagesOnThePathDoNotCrash`, `firstRunFixNowThenPickerDoesNotCrash`, `firstRunPhoneDetourDoesNotCrash`); `SettingsBackLadderTest.everyOverlayAndDepth` extended to depth 5 (8 rows fail before).

### C-B2 = D-B1 = D-B2. PIN-gated actions ran without the PIN: group-manager Unlock/Reset, Restore and Restore now, and (with "Lock settings") the Playlists menu's Edit/Remove
- **Where:** core: `SettingsMachineImpl.kt:485-501` (`menuKey`: a menu option always emitted `RowIntent.Menu`, the PIN gate was never consulted), `SettingsContracts.kt` (`ChoiceOption`, `RowKind.Item.menu`: no way to mark an option as needing the PIN), `ChannelsRows.kt:187-198` (`ChannelsPages.groupItem`: Unlock and Reset), `BackupRows.kt:213` (`backup.restore`, `RowKind.Action()`) and `:292-294` (`restore.go`), `PlaylistPages.kt:99, 101` (Playlists section menu: Edit → `Push(PlaylistSource)`, Remove → confirm → remove; the same actions on the Playlist page carry `needsPin = lockSettings()`, `:174, :196`). Data: `ChannelsPagesImpl.kt:233-235` (`M_UNLOCK` → `lockGroup(false)`, `M_RESET` → `deletePrefs`) → `ParentalSessionImpl.setGroupLocked` (no session check); `BackupRows.kt:152-175` (`BackupPageState` had no PIN state); `BackupPagesImpl.kt:162, 170-183, 343-369, 444-449` (the phone's RESTORE path went straight to RestorePreview); `GroupAdminDao.entries` (`GroupAdminDao.kt:35-42`, lists locked groups whatever the access); `BackupRestorer.clearUserRows` (`BackupRestorer.kt:366-378`).
- **Problem:** §3.9.2: "Remove playlist, Edit source, Restore backup, Reset The Box (with Lock settings on, or always for Restore and Reset when a PIN is set); Lock/Unlock in the channel or group menu → `SettingsAction(token)`". With a PIN set and the session locked, a child opens Settings ("Lock settings" is off by default), Channels and groups → Groups → long OK on an adult group → **Unlock**: `group_prefs.locked = 0` is written, and by §4.3 (S5) an explicit group decision beats `is_adult`, so the group is permanently unlocked and visible in every list (`TuneGuard.check` of an adult channel returned ALLOWED). **Reset** on a group the parent locked deletes the explicit lock the same way. **Restore → Replace** with an older backup (the weekly auto-backup in `Download/TheBox` is on by default, so one from before the parent set things up usually exists) imports the `parental` policy domain and `group_prefs`/`channel_prefs.locked` and clears every lock of the affected playlists, with no PIN, from Restore → From a file, From Downloads, the phone's RESTORE purpose and Restore now. With "Lock settings" on, the Playlists section's item menu edited and removed playlists with no PIN although the Playlist page's own rows ask. The guide's own group menu asks (`GuideStateMachineImpl.lockAction`), so the bypass was only through Settings. It defeats the parental feature, a must-have row of M5 (a security defect). Reproduced: `groupManagerUnlockAsksForThePin` ("Unlock ran without the PIN"), `groupManagerUnlockDoesNotBypassTheLockedSession` (`expected:<NEEDS_PIN> but was:<ALLOWED>`), `restoreRowIsPinGated` ("BackupPageState has no pinSet at all").
- **Fix (lead decision 1):** `ChoiceOption.needsPin` (additive); `SettingsMachineImpl.menuKey` runs a `needsPin` option through `gated`; `ChannelsPages.groupItem` Unlock and Reset `needsPin = pinSet`; `PlaylistsSectionPage` Edit and Remove `needsPin = lockSettings()`; `backup.restore` and `restore.go` `needsPin = pinSet` (`BackupPageState.pinSet`, `PreviewState.pinSet`, filled by `BackupPagesImpl` from `ParentalSession.state`); `DiagPages` "Edit login" `needsPin = lockSettings()` (`:ui`). Defence in depth: `ParentalSessionImpl.setGroupLocked(false)` (`refusesLowering()`), `ChannelsPagesImpl` Unlock/Reset and `BackupPagesImpl` Restore now refuse while a PIN is set and access is not OPEN. `BackupRestorer` has no session access and is unchanged.
- **Tests:** `SettingsMachineReviewFixTest.menuOptionWithNeedsPinRunsOnlyAfterTheGrant`; `ReviewFixRowsTest.groupManagerUnlockAsksForThePin` (adopted), `.unlockAndResetNeedThePinWhenSet`, `.restoreAndRestoreNowNeedThePinWhenSet` (adopted; it sets `pinSet`, because the ruling is `needsPin = pinSet` and the reviewer's row asserted it with no PIN); `SetupPagesTest.playlistMenuEditAndRemoveAskWithLockSettings`; `:data` `ParentalReviewFixTest.groupManagerUnlockDoesNotBypassTheLockedSession` (adopted). The refusal in `BackupPagesImpl` has no JVM test.

### D-B3 (+ D-S2). "Export logs → To your phone" never reached the phone, and offered files were never removed

### D-B4. The updater abandoned its install session at the moment it showed the system confirmation
- **Where:** `UpdaterImpl.kt:368-372, 387-395` (`watchUnansweredConfirmation`); `InstallResultReceiver.kt` `onReceive` (`PENDING_USER_ACTION` → starts the confirmation, then calls the listener).
